# Commercial Due Diligence in SQL: Is This Retailer's Customer Base Healthy?

**Scenario (hypothetical):** a private equity fund is evaluating an acquisition of a UK online gift
retailer and asks: *Is revenue growth real and repeatable, or bought with one-off customers, price rises
and a few big accounts?* This is the "customer cube" analysis that consulting and PE due-diligence teams
run in the first week of a deal, built here as a tested, layered **SQL** model on DuckDB.

## Questions answered (one SQL mart each)

| # | Diligence question | Mart | Technique |
|---|---|---|---|
| 1 | How is the business trending? | `mart_monthly_kpis` | Revenue, orders, AOV, new-customer revenue, cancellations |
| 2 | Do customers come back? | `mart_cohort_retention` | Monthly acquisition cohorts, `datediff`, retention matrix |
| 3 | Who are the customers? | `mart_rfm`, `mart_rfm_summary` | RFM scoring with `NTILE(5)` window functions and segment rules |
| 4 | Is revenue concentrated? | `mart_concentration` | Running sums, Lorenz curve, top-1/10/20% share |
| 5 | What drove growth? | `mart_customer_bridge` | FY bridge: new vs lost vs retained (up and down) customers |
| 6 | Price or volume? | `mart_price_volume` | Price, volume, new-product and discontinued-product effects |
| 7 | Where is it sold? | `mart_country` | Country mix and growth |
| 8 | What is a customer worth? | `mart_cohort_value` | Cumulative revenue per customer by cohort |

## Architecture

```
raw Excel (UCI) ──► Parquet ──► 01_staging.sql ──► 02_core.sql (star schema) ──► 03_marts.sql ──► 04_checks.sql
                                 cleaning rules     fct_sales, fct_orders,        8 analysis       reconciliation,
                                                    dim_customer, dim_product     marts            bridge integrity
                                                                                       │
                        outputs/dd_findings.md  ◄── run_pipeline.py ──► Streamlit dashboard + SQL explorer
```

**Data-quality checks run on every build** and fail it if broken. The fact table must reconcile to staging,
both bridges must add up exactly, and retention at month 0 must be 100%. That last check caught a real bug
during development: customers whose first record was a *cancellation* were being put into the wrong cohort.

## Run it

```bash
python -m venv .venv && source .venv/bin/activate     # Windows: .venv\Scripts\activate
pip install -r requirements.txt
python run_pipeline.py      # downloads ~45 MB once; the first Excel read takes a few minutes
streamlit run app.py
python -m pytest -q         # 6 tests on hand-made data where every answer is known
```

If the download fails, get *Online Retail II* from the
[UCI ML Repository](https://archive.ics.uci.edu/dataset/502/online+retail+ii) and put the `.xlsx` in `data/`.
`--sample` runs on synthetic data for an offline smoke test only.

## Outputs
`outputs/dd_findings.md` (answer-first memo with red and green flags), one CSV per mart, charts, `metrics.json`
and `resume_bullets.md`, all generated by code from the real data.

## Cleaning decisions (and why)
* Invoices starting with `C` are cancellations. They're kept as negative revenue, so revenue is net.
* Stock codes with no digits (postage, bank charges, manual adjustments) are excluded from product analytics.
* Price <= 0 lines are excluded. Exact duplicate rows are removed.
* Lines without a customer ID count in revenue but not in customer metrics. The checks report their share.
* The fiscal year runs Dec-Nov, which gives two complete, comparable 12-month periods.

## Limitations
* There is no cost or margin data, so the analysis is revenue-based and CLV means revenue, not profit.
* Customer behaviour before Dec 2009 is unknown, so the earliest cohorts include customers acquired before the data starts.
* Red/green thresholds in the memo are judgement calls, and the memo states them.
